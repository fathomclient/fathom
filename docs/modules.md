# Modules

Every module Fathom ships, what switching it on actually does, and what it can be
configured with.

This document is generated by hand from
`minecraft/fathom-optimizations/src/main/java/net/fathom/optimizations/core/module/Modules.java`
and kept honest by `ModuleTests`, which fails the build if anything below stops
being true.

---

## 1. The rule

**A visible toggle changes the game.**

The client previously shipped with modules whose switches changed a boolean that
nothing read. FPS and Coordinates worked; several others looked identical, did
nothing, and there was no way to find out except to try them. That teaches people
that Fathom's controls are decorative, which is worse than not offering the
module at all.

So the rule is enforced by the model rather than by discipline:

| Concept | Where it lives | What it guarantees |
| --- | --- | --- |
| `Implementation` | `core/module/Implementation.java` | `WORKING` and `EXPERIMENTAL` get a toggle. `UNAVAILABLE` gets **no toggle at all** — the row says why instead. |
| `FathomModule.hasEffect()` | `core/module/FathomModule.java` | True only when the module drives a HUD widget, an optimization, or a named behaviour. |
| `Behaviour` | `core/module/Behaviour.java` | The list of hooks the client implements. A module naming one that does not exist fails the build; a hook nothing names fails too. |
| `ModuleTests` | `src/test/.../ModuleTests.java` | Asserts all of the above, and prints the toggle validation table in §4. |

There is no state for "declared but not wired". A module either does something or
it is `UNAVAILABLE` and has no switch.

## 2. One switch per module

A widget used to have two switches: its module's, and an `enabled` flag on its
placement in the HUD layout. The shipped layout said disabled for nine of the
eleven widgets, so switching a module on merely *permitted* its widget while the
layout kept it hidden.

`Placement.enabled` is gone. A widget is drawn when the module that owns it is
on — `ModuleRegistry.widgetAllowed` — and that is the only question anyone asks.
The HUD page's toggle and the Mods page's toggle are the same boolean, and the
editor's "Hide" switches the module off rather than setting a flag beside it. A
`widget.*.enabled` line written by an older build is read and discarded.

`HudTests.aWidgetIsDrawnOnlyWhenItsModuleIsOn` asserts by reflection that neither
`Placement.enabled` nor `Widget.onByDefault` has come back.

## 3. The modules

Position, anchor and scale are not settings for any HUD module: they are spatial,
and they are set by dragging in the HUD editor. Every HUD module except the
crosshair also carries the eight common style settings from `HudStyle` — text
colour, text shadow, background, background colour, background opacity, padding,
corner radius, drop shadow — declared in one call and read in one place
(`TextWidget`), so they cannot drift apart.

| Module | Category | State | Effect | Needs | On by default | Its own settings |
| --- | --- | --- | --- | --- | --- | --- |
| FPS | HUD | Working | `fps` widget | — | **yes** | Smoothing (Off/Light/Smooth), Format |
| Coordinates | HUD | Working | `coordinates` widget | A world | **yes** | Show X/Y/Z, Axis labels, Decimal places, Direction, Biome |
| Clock | HUD | Working | `clock` widget | — | no | Format (12/24 hour), Seconds, Time zone (System/UTC) |
| Pack Display | HUD | Working | `pack-display` widget | — | no | Format |
| Ping | HUD | Working | `ping` widget | A server | no | Format, Colour by quality |
| CPS | PvP | Working | `cps` widget | — | no | Buttons (Both/Left/Right), Sample window, Label |
| Keystrokes | PvP | Working | `keystrokes` widget | — | no | Movement keys, Mouse buttons, Space bar, Sneak key, CPS on buttons, Pressed colour, Unpressed colour |
| Armour HUD | PvP | Working | `armour` widget | A world | no | Held item, Slot names, Style (Percent/Remaining) |
| Potion HUD | PvP | Working | `potions` widget | A world | no | Level, Time left |
| Sprint and sneak | Utility | Working | `toggle-sprint` widget | A world | no | Show sprinting, Show sneaking |
| Zoom | Utility | Working | `zoom` behaviour | A world | no | Amount, Lower sensitivity, Smooth camera, Animate — plus its keybind |
| Crosshair | Visual | Working | `crosshair` widget + `crosshair` behaviour | A world | no | Shape, Size, Gap, Outline, Hide vanilla crosshair, Colour |
| Unfocused FPS limit | Performance | Working | `input.unfocused-fps-cap` | — | **yes** | Limit |

Nothing is currently `UNAVAILABLE`. If something becomes so — a hook that a
future Minecraft version removes, say — it loses its toggle and keeps its row.

### 3.1 Notes on particular modules

**Ping** reads the latency the multiplayer connection already reports, which is
the number the tab list shows. There is no separate probe anywhere in the client:
inventing one would mean traffic the server did not ask for, to measure something
it already tells us. In singleplayer the number is zero and useless, so the module
declares `MULTIPLAYER` and its row says "Only on a multiplayer server".

**CPS** counts presses the player made at the game. Clicks are ignored while a
screen is open, while the window does not have focus, and before a player exists,
so arranging the HUD or clicking back into the window does not inflate the
number. The sample window is a setting; a longer window reports the same rate
measured over more evidence, not a larger count.

**Zoom** divides the field of view vanilla computed for this frame, at
`GameRenderer.getFov(FZ)F`. It does not write `GameOptions.fov`, because that
value is saved to disk — a client that crashed while zoomed would come back
permanently at 25 degrees. Mouse sensitivity and the smooth camera are restored
exactly as they were the moment the key is released.

**Crosshair** hides vanilla's by cancelling `InGameHud.showCrosshair()Z`, and the
setting that does so can be switched off, because drawing both is a reasonable
thing to want while deciding between them.

**Pack Display** has no icon setting. 1.8.9 does not keep a decoded pack icon
after the resource reload finishes, so drawing one means re-reading and uploading
a texture from inside a HUD renderer. A setting that switched on an icon which
never appeared is the exact defect this milestone removed, so the setting is
absent rather than inert.

## 4. The toggle validation table

Printed by `ModuleTests`, which fails if any row is not five passes.

```
  Module              state  appears  disappears  persists  isolated
  ------------------  -----  -------  ----------  --------  --------
  FPS                 yes    yes      yes         yes       yes
  Coordinates         yes    yes      yes         yes       yes
  Clock               yes    yes      yes         yes       yes
  Pack Display        yes    yes      yes         yes       yes
  Ping                yes    yes      yes         yes       yes
  CPS                 yes    yes      yes         yes       yes
  Keystrokes          yes    yes      yes         yes       yes
  Armour HUD          yes    yes      yes         yes       yes
  Potion HUD          yes    yes      yes         yes       yes
  Sprint and sneak    yes    yes      yes         yes       yes
  Zoom                yes    yes      yes         yes       yes
  Crosshair           yes    yes      yes         yes       yes
  Unfocused FPS limit yes    yes      yes         yes       yes
```

What each column means:

- **state** — the toggle changes the module's own boolean, both ways.
- **appears** — with it on, the thing it drives is reachable, asked of the *same*
  `widgetAllowed` and `SwitchBoard` the renderer and the client use. Testing a
  copy of the rule would have passed while the client was broken.
- **disappears** — with it off, it is not.
- **persists** — written and read back through `ModuleStore` into a fresh
  registry.
- **isolated** — written in one game directory and not visible from another.

### 4.1 What the table does not prove

That the widget looks right, that the zoom feels right, or that a setting has the
effect its label claims. Those need a running game and eyes, and the table is
deliberately not written to imply otherwise.

Those were then checked by hand, once, at 1280x720 with GUI scale 3 in a
singleplayer creative world: every module above was switched on and drew, a
Format change moved the FPS readout on the next frame, Zoom narrowed the field of
view, and the crosshair Mixin hid vanilla's. See the mod's README for the full
list, including what that session did **not** cover — no other resolution, no
multiplayer, and no mouse-button keybind.

## 5. Settings are a schema, not a screen

`Setting.Kind` has seven members, and `ModsSection` renders each one:

| Kind | Control | Used for |
| --- | --- | --- |
| `TOGGLE` | switch | on/off |
| `SLIDER` | track | "roughly where in this range" — zoom amount, crosshair size |
| `INTEGER` | stepper | "exactly how many" — padding, decimal places, sample window |
| `CHOICE` | dropdown | one of a short list |
| `COLOUR` | swatch | a colour, from a palette |
| `TEXT` | field | a short string, length-capped so it cannot push a widget off screen |
| `KEY` | rebinding control | a key belonging to a value rather than to the module |

A module that adds a setting gets a control for it without the interface
changing. That is why `HudStyle.declare` can add eight settings to a module in
one call and have all eight appear, laid out identically to everything else.

### 5.1 Keybinds

A binding is None, a keyboard key, or a mouse button. Mouse buttons use
Minecraft's own encoding — `button - 100`, so the left button is `-100` — which
means a Fathom binding and a vanilla binding are the same number for the same
button.

Conflicts are **shown, not forbidden**: the drawer writes *"This key is also used
by Zoom."* under the control and lets the binding stand. Two modules on one key
is usually a mistake and occasionally exactly what somebody meant; refusing it
would be wrong in the second case with no way round, and saying nothing would be
wrong in the first, which is the common one.

## 6. Where settings are stored

| What | File, relative to the profile's game directory |
| --- | --- |
| Module switches, setting values, keybinds | `config/fathom-features.properties` |
| HUD layouts | `config/fathom-hud.properties` (and one file per named layout) |

Both are written under the game directory the launcher hands the game, and the
launcher gives each profile its own — `profiles/<id>/minecraft`, unless the user
deliberately points a profile at a directory they chose. So per-profile storage is
a consequence of the path rather than a feature of the store, which is exactly
why `ModuleTests.oneProfileDoesNotSeeAnother` exists: it would be lost silently
the day something decided to resolve the path for itself.

Only changed values are written. A file listing every default is a file where a
real change is invisible, and it freezes a default that later improves.

## 7. What a switched-off module costs

Nothing per frame, and this is checked by construction rather than measured:

- A widget whose module is off is skipped before it is measured or drawn —
  `FathomHud.render` asks `widgetAllowed` first.
- Mouse sampling for CPS and Keystrokes is skipped entirely when neither module
  is on. It is the only per-frame work here that is not free.
- The zoom hook returns `1f` and does no allocation when the module is off, the
  key is unbound, or a screen is open.
- With the hub closed, no settings interface exists: the sections are objects on
  a screen that is not instantiated.
