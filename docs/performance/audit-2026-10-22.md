# Performance audit for Bedwars-style minigames — 2026-10-22

Where a Hypixel Bedwars (and SkyWars, Duels, practice lobby) frame goes that
the existing multiplayer work has not already covered, what was built from it
today, and what to do next, in order. Builds on `multiplayer-2026-10-13.md`
(ranked bottlenecks, sign and frame fixes, tab list replay) and
`multiplayer-2026-10-20.md` (held item vertex reuse, model box batching).

Nothing in this document is a whole-frame timing claim: the one timed A/B
started today was stopped because the machine was not quiet (a browser,
Discord and another game were running). Findings are from vanilla and OptiFine
bytecode plus the measurements in the two earlier documents.

## 1. What a Bedwars game has that the benchmark scenes do not

The `mp-bench` scenes cover crowds, labels, holograms, generators, signs and
the tab list. A Bedwars game adds three things none of them exercise:

| Event | What the client does | Where |
|---|---|---|
| **Placing blocks (bridging)** | Every block change re-runs lighting for that position (`World.setBlockState` → `checkLight`), and the render chunk the camera is in is rebuilt **synchronously on the render thread** ("build near" in `WorldRenderer.setupTerrain`); every other dirty chunk goes to the worker threads | vanilla, also in OptiFine M5 |
| **TNT and fireballs** | `Explosion.affectWorld` on the client breaks every affected block (each one lighting + chunk rebuild), plays the sound, and adds **two particles per broken block** plus one large burst — a blast through a wool base is hundreds of particles simulated for a second or more | vanilla |
| **Generator piles** | Dozens of ingot/diamond/emerald entities on each generator, each drawn as up to five copies of its model (`ItemEntityRenderer.method_10222`), each copy rebuilt vertex by vertex every frame | vanilla, OptiFine |

## 2. Findings, ranked

"Estimate" is from the per-item and per-label costs already measured, not a new
timing.

| # | Finding | Evidence | Estimate | Risk | Status |
|---|---|---|---|---|---|
| 1 | **Dropped items rebuilt every frame.** A generator pile is the same few models drawn up to 5 times per entity per frame; held items got vertex reuse on 10-20, dropped items did not | Model share of a dropped item: 4.4 µs of 7 (10-13 §4, #4). Held items went 8.9 → 5.2 µs with the same technique | 0.1–0.3 ms a frame beside a busy generator (40–60 copies); more with 160 items | Low: same code path and gate as held items | **Built, gate passed, off until measured** (§3) |
| 2 | **Explosion particles.** Two particles per broken block on top of the blast; particle physics was already the largest p99 cost in combat scenes (1.1 ms a tick with particles, 10-13 §4 #3) | `Explosion.affectWorld` bytecode: 4 `addParticle` calls, the 3rd and 4th per block | Removes most of the particle spike after TNT; visual change, so a setting, not an optimization | None (opt-in) | **Built** as Particles → Explosion particles (All / Fewer / None) |
| 3 | **Your Forge profile has OptiFine Render Regions off.** | Measured 10-20: terrain 0.56 ms (Forge, off) against 0.29 (Fabric profile, on) | ~0.27 ms a frame, every frame | None | **Setting to change**: Video Settings → Performance → Render Regions: ON |
| 4 | **Synchronous "build near" while bridging.** The camera's own render chunk rebuilds on the render thread the frame a block in it changes | `WorldRenderer.setupTerrain` ("build near" → `updateChunkNow`) | A 16³ section with terrain is ~0.5–2 ms; bridging places 5–10 blocks a second, so periodic spikes rather than average cost | Medium: async rebuild shows a placed block one frame later; OptiFine patches this method; needs a pixel/visual check | **Next** — needs a bridging scene first (§4) |
| 5 | **Client light updates on every block change.** Sky light over the void recomputes down the column; an explosion runs it once per broken block | `World.setBlockState` → `method_8568` (checkLight) on the client | Spikes after TNT; not an average cost | High: deferring or skipping produces wrong lighting — very likely the same family as the "dark blocks after TNT" bug already reported | **Not recommended** without a correctness design |
| 6 | **Resting dropped items still run physics every tick.** Each client-side item applies gravity and a full collision query (`move`) every tick even when lying still | `ItemEntity.tick` | Part of the 0.6–1.0 ms tick (10-13 §4 #3) with 160 items | Medium: client-side simulation; must stay identical to what vanilla computes | **Candidate**: skip only when provably a no-op (on ground, zero motion, no block change below) with a verify mode |
| 7 | **Nametags module bypasses the cached nametags.** With Nametags on, labels are drawn directly instead of through the display-list fast path | `Nametags.render` runs before `NametagRenderer` | ~1 µs more per label with the module on; nothing with it off | Low | **Known cost**; could feed the style into `NametagRenderer` later |
| 8 | **New modules' idle cost.** Every module added this session is off by default; with it off its hook is one hash-map lookup per entity, label, text draw or weather query | `ModuleRegistry.find` is a `HashMap.get`; `NickHider.apply` returns on a boolean first | Negligible (well under 0.01 ms a frame) | — | No action |
| 9 | **Armour HUD allocates ~136 bytes a frame.** The in-game self-test's HUD allocation budget (256 bytes a frame) fails intermittently with armour at 136 of ~275 | Self-test, several runs today | Tiny (≈40 KB/s at 300 fps), but it is the one widget over its share | Low | **Candidate**: find the allocation in `ArmourWidget` |

Already done and measured before today, so not repeated here: held items and
model boxes (largest crowd costs), tab list text, sign text, item frames,

## 3. Built today

### Dropped item vertex reuse — `render.entity.dropped-item-models` (off until measured)

`ItemEntityRendererModelListMixin` opens the same replay window around
`ItemEntityRenderer.render` that `HeldItemFeatureListMixin` opens around the held
item layer, so a dropped item's model goes through `ItemModelLists` exactly as a
held one does: first draw kept, later draws handed back to the tessellator in
one copy through the game's own upload path; transforms (including Item
Physics'), the glint and OptiFine's custom items stay live; tinted and emissive
models stay live. The window restores whatever it found, so a held item inside
it is unaffected.

**Correctness (Forge + OptiFine M5, `generators` scene, `fathom.verify.caches`):**
33,450 replays, 1,045 drawn both ways offscreen under live matrices, all with
pixels drawn: **0 differing**; vertex data 1,045 compared, **0 differed**. Item
models replayed per frame went from 8 (held only) to 168.

**Timing: not measured.** The 6-round A/B was stopped (machine not quiet). The
entry stays off by default (`defaultOnWhenMeasured`) until a paired win is
recorded. To measure it:

```
python tools/mp-bench/compare_builds.py --forge --jar cur=minecraft/fathom-optimizations/build/libs/fathom-forge-0.3.0-hud.jar \
    --order cur --scenes mp-empty,generators --arms normal,on:render.entity.dropped-item-models \
    --rounds 6 --seconds 4 --bots 16 --tag drop-ab
python tools/mp-bench/paired_windows.py minecraft/fathom-optimizations/run-mp/logs/fathom-mp-drop-ab-cur-1-console.log
```

### Explosion particles (Particles module)

`ExplosionParticlesMixin` redirects the two per-block `addParticle` calls in
`Explosion.affectWorld` (ordinals 2 and 3); the blast itself (0 and 1) is always
drawn. All is vanilla; Fewer keeps one in four; None drops them. Blocks,
damage, knockback and sound are untouched. `require = 0`, so a reworked method
leaves vanilla's particles rather than failing to start.

## 4. Next, in order

1. **Measure dropped item reuse** on a quiet machine (command above) and turn it
   on by default on a paired win.
2. **Turn on Render Regions** in the Forge profile's OptiFine settings (free,
   already measured).
3. **Add a `bedwars` scene to `mp-bench`**: 8–16 players on islands, generators,
   a player bridging (a block placed every 150 ms beside the camera) and a TNT
   blast every few seconds, so #4–#6 can be measured rather than estimated.
4. **"Build near" off the render thread** (#4), gated by that scene and a check
   that a placed block is never missing for more than one frame.
5. **Resting item physics** (#6), only with a verify mode proving positions are
   identical to vanilla's.
6. **Armour HUD allocation** (#9).
7. Lighting (#5) only as a correctness project, starting from the reported
   "dark blocks after TNT" bug, not as an optimization.
